AI on the Merkle DAG

Language models are good at reading and writing what people currently do by hand: explaining diffs, drafting notes, triaging findings, writing the narrative for leadership. Models are bad at numbers they did not compute, and at being trusted without evidence. The Merkle DAG supplies the evidence: every fact an AI states can be checked against a hash, and every action it proposes runs through the same guardrails as a person's.

What the orchestration platforms are shipping (November 2026)

From the vendors' own docs and release notes; the sources are at the foot of the page.

Dagster+ AI (Compass)

  • Chat over runs, assets and metadata, in the UI, Slack or Teams
  • Root-cause analysis of failed runs from logs, with follow-up questions
  • Proactive monitoring that scans deployments and opens Issues
  • Dispatch a coding agent from an Issue to open a fix PR
  • An MCP server, plus skills for coding agents

MLflow 3

  • Tracing of LLM and agent calls as nested spans
  • LLM judges (built-in and custom) and code-based scorers
  • The same judges run online over production traces
  • An AI assistant, dashboards and judge optimization from feedback (3.9)

Apache Airflow (common-ai provider)

  • LLM operators: single call, batch, file analysis, branching, SQL
  • @task.llm and @task.agent decorators; 20+ model providers
  • An MCP toolset and SQL toolsets for agents
  • Human approval for LLM and agent steps (3.4); an official MCP server is proposed (AIP-91)

The common pattern: a chat that reads the orchestrator's metadata, AI root-cause analysis, proactive issue detection, agents that propose fixes as pull requests, judges that score text, an MCP server so any agent can use the platform's tools, and human approval on anything that acts. All of it fits here, and the Merkle DAG adds what the others lack: per-layer hashes and exact lineage that turn an AI's explanation into something checkable.

Design principles

Numbers come from tools, never from the modelThe model writes prose with placeholders; values are filled in from the results store. A verifier checks every number in the text against its source.
Every claim cites a hash"steel_estimation config changed" links to the config sha and the diff. Uncited claims are rejected.
Equality and gates stay deterministicWhat changed is decided by sha comparison. AI can explain and rank; it never decides what counts as changed, and it never passes a gate.
Agents propose; people signAgents draft run plans, PRs and notes. Sign-off, waiving a warning and release stay human, bound to hashes.
AI runs are recorded tooModel, prompt version, tool calls and outputs go into the run record as observational data (not hashed), so an audit can see what the AI said and why.
Evaluate against past auditsPast findings, returns and sign-offs are a ready-made eval set: did the AI flag what the manager flagged?

Autonomy ladder

0 · ExplainRead-only: summaries, Q&A, narratives.All use cases start here.
1 · DraftWrites run plans, notes, PR descriptions for a person to edit.
2 · Act in exploratoryRuns exploratory and sweep runs; never publishable.
3 · Propose to productionOpens PRs and candidate runs; CODEOWNERS and gates apply.
NeverSign off, waive a warning, accept a failure, release, edit the manifest directly.

The tool surface: an MCP server for the Merkle DAG

One server exposes the platform to any agent (Claude, coding agents, Slack bots), with each tool tagged by the autonomy rung it needs.

read (rung 0)                                  write (rung 1–3, policy-checked)
  get_run(run_id)          → run record          validate_plan(plan_yaml)    → errors, impact set
  trace(node, run_a, run_b)→ root causes, edges  draft_run_plan(intent)      → plan_yaml (rung 1)
  diff(node, layer, a, b)  → git / YAML / CSV    start_run(plan, tier)       → exploratory only at rung 2
  impact_set(change)       → descendant nodes    open_pr(repo, branch, diff) → rung 3, CODEOWNERS
  findings(run_id)         → guardrail results   comment(finding_id, text)   → rung 1
  results_query(spec)      → rows + output shas  notify(owner, task)         → rung 1
  manifest(cycle)          → pins, vintages
  history(node, n)         → past params, values, sign-offs

  • Failure triage for runs
  • Consistency judge on intent notes

Phase 3 · quarter 2Agents with approvals
  • Upstream cascade agent
  • Data refresh agent
  • Guardrail fix-PR agent
  • Sweep agent; release packet agent
Needs: write tools behind the autonomy policy, human approval steps.

Risks and controls

RiskControl
A fabricated or wrong number in a narrative reaches the CEONumbers only through placeholders filled from the results store; a verifier re-reads every number and its output sha; failing text is blocked.
A confident but wrong explanation of a deltaExplanations must cite the trace (root-cause nodes and layers from sha comparison); a judge checks the explanation against the diff; the human signs.
An agent changes productionThe autonomy ladder enforced in the MCP server: production writes only as PRs through CODEOWNERS and the release gate.
Automation bias: reviewers stop lookingThe audit shows the AI's ranking next to the raw findings; sampled spot checks; disagreements tracked as an eval metric.
Cost and latency at 20 owners × 40 runsBatch calls for nightly summaries, prompt caching for the shared pack context, and a small model for routing and triage.
Reproducibility of AI outputAI output is observational, never an input to a node's hash; model and prompt versions are recorded with each output.
