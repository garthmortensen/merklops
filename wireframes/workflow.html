Model lifecycle on the Merkle DAG

Twenty model owners, each with a few feature releases a year, about ten reruns a quarter, quarterly and annual data, upstream changes that ripple downstream, and a manager audit before the CEO sees anything. This page maps that work, names where human error gets in, and recommends a workflow that the hashes can police.

One owner's year, mapped

Most of the volume is repetition: reruns and cascades, not code. That is where caching, templates and automatic checks pay off.

× 20 owners: about 800 reruns and 60 feature releases a year feed one quarterly release of the full DAG.

Recommended changes

01A cycle manifest

One reviewed file per quarter pins every node's code tag, the parameter set, each source's data vintage, the metadata and the release image. Every run in the cycle starts from it; anything different is an explicit override in a run plan.

# cycles/2026Q4.yml
image: sha256:7d1e…
metadata: {jump_off_year: 2025, region: national}
data: {bls_quarterly: v2026-03, bea_annual: v2025, static: v1}
nodes:
  steel_estimation: {ref: v0.2.0, params: {drift_window: 20}}
  …
Stops: wrong code version, wrong vintage, wrong parameter

02Three run tiers

Exploratory: anything goes, never publishable or signable. Candidate: tags only, release image, validated parameters. Release: manifest-locked, full tests, audited. Guardrails tighten with the tier, so exploring stays fast.

Stops: laptop runs reaching production

03Typed, ranged parameters

The pack declares each parameter's type, unit, allowed range, default and owner. The UI offers only valid values; a candidate run with an out-of-range value fails before it starts.

Stops: typos, unit mistakes

04Parameter sweeps as one object

Instead of ten separate reruns, define a sweep: one base plus N variants. It runs as a batch (unchanged nodes are cache hits), compares the variants side by side, and promotes the chosen one to a candidate with its intent note.

Cuts: repetitive reruns; keeps every variant traceable

05Declared intent on every run plan

Each run plan states what should change ("steel drift window 20 → 15; expect steel and cost_index to move"). The Merkle DAG computes the expected impact set, and the audit compares it with what actually changed.

Stops: silent side effects, wrong node edited

06A data calendar

Each source carries its cadence (quarterly, annual, static) and the vintage expected in each cycle. Due sources are fetched and tagged once, for everyone, and the manifest picks them up.

Stops: mixed vintages across owners

07Automatic upstream cascades

When an upstream owner's signed-off output hash changes, the platform computes the downstream impact set, runs it (with cache), and opens a review task for each affected owner showing "changed because upstream" with the trace.

Stops: stale upstream; removes manual "rerun everything"

08Sign-offs bound to hashes

An owner signs a node's input hash, not a date. If anything upstream changes afterwards, the sign-off expires and the owner is asked again.

Stops: approving numbers that later changed underneath

09Release pipeline as CI

Feature branch → check-pack and unit tests → candidate run → regression tie-out (identical hash, or explained by a declared change) → UAT on the dashboards → tag → manifest pull request → manager audit → release.

Automates: regression testing and tie-out

10Ownership in the repo

CODEOWNERS on nodes/*.yml: owners change only their nodes; the platform team owns model_lib, the pack, the environment and the manifest structure. Every change has one accountable reviewer.

Stops: editing someone else's node by mistake
